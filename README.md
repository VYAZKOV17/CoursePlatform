# CoursePlatform

## 1. Описание проекта и решаемая проблема
CoursePlatform — платформа онлайн-курсов, на которой:
·	**Instructor** создаёт курсы, состоящие из модулей и уроков;
·	**Admin** модерирует курсы перед публикацией (проверка соответствия заявленному описанию);
·	**Student** просматривает каталог опубликованных курсов, записывается, проходит уроки, отслеживает прогресс и получает сертификат по завершении.
Проблема, которую решает система: дать простой, предсказуемый flow «запись → обучение → подтверждение результата» без лишней сложности (без оплаты, подписок и сложной ролевой иерархии) — минимальный жизнеспособный набор функций для образовательной платформы.
## 2. Цели и границы системы
Цели:
·	Управление курсами и их модерация
·	Запись студента на курс и контроль дублирующих активных записей
·	Отслеживание прогресса прохождения курса (упрощённо — процент)
·	Выдача сертификата по завершении курса
·	Уведомления через внешний Notification Service (SMTP)

## 4. Архитектурный обзор
Архитектура описана по модели C4 на трёх уровнях — от общего контекста до внутренних компонентов API:
·	**Context** — CoursePlatform как единая система, три актора (Student, Instructor, Admin), один внешний сервис — Notification Service (SMTP)
·	**Container** — Web Application (React), API Application (Node.js), Database (PostgreSQL)
·	**Component** — декомпозиция API Application: Auth, Course Management, Enrollment, Certificate

8. Как посмотреть диаграммы
Все диаграммы — в формате PlantUML (.puml). Варианты просмотра:
1.	VS Code — расширение PlantUML, Alt+D для предпросмотра
2.	Онлайн — вставить содержимое файла на plantuml.com/plantuml
3.	CLI — plantuml docs/**/*.puml (требует Java + plantuml.jar)
C4-диаграммы (03-c4-architecture/) используют библиотеку C4-PlantUML, подключаемую через !include — для рендеринга нужен доступ в интернет либо локальная копия библиотеки.

11. Ключевые решения и допущения
Полный список — в ASSUMPTIONS.md. Кратко, самое важное:
·	Enrollment смоделирован как association class между Student и Course — не отдельная независимая сущность
·	Повторная запись на курс после отписки (dropped) разрешена — уникальность обеспечена частичным индексом только среди active-записей
·	Progress не выделен в отдельную таблицу — упрощён до progress_percent на Enrollment (осознанное решение для pet-проекта)
·	Пользователи — через Class Table Inheritance (users + students/instructors/admins)
·	Payment полностью вне скоупа — Notification Service (SMTP) единственная внешняя интеграция
12. Что демонстрирует проект (для рекрутера)
·	Формализация требований: атомарные User Stories по INVEST с тестируемыми Acceptance Criteria (Given/When/Then), включая негативные сценарии
·	Сквозная трассируемость: одно и то же бизнес-правило (например, «нельзя получить сертификат при незавершённом курсе») видно на всех уровнях — от AC в User Story, через альтернативный поток Use Case и ветвление в Sequence Diagram, до 400 Bad Request в OpenAPI и CHECK-constraint в SQL
·	Архитектурное мышление на разных уровнях абстракции: от C4 Context для бизнеса до Component diagram для разработчиков, без противоречий между уровнями
·	Владение нотациями: Use Case, Class, Sequence, Activity, State Machine, ER — с корректным использованием кардинальности, типов связей (ассоциация/композиция/наследование) и условных конструкций (alt, repeat)
·	Проектирование данных «по-взрослому»: осознанный выбор паттерна наследования (Class Table Inheritance), частичные индексы для нетривиальных бизнес-правил уникальности, явное разделение того, что моделируется constraint'ом в БД, а не только проверкой в коде
·	API-дизайн, согласованный с доменной моделью: коды ответов выведены из конкретных диаграмм, а не придуманы «для полноты»; переиспользуемые схемы; единая обработка ошибок
13. Возможные улучшения
Если бы проект развивался дальше:
·	Payment/Subscription домен — если в скоуп добавляются платные курсы, потребуется новый Use Case, класс Payment, внешняя система в C4 Context, новый Sequence Diagram и таблица payments — по шаблону, использованному для остальных этапов
·	Раздельный трекинг прогресса по урокам — сейчас хранится только агрегированный progress_percent; для более точной аналитики можно вернуться к отдельной таблице lesson_progress (архитектурно предусмотрено, но осознанно отложено)
·	Обработка изменения состава курса после публикации — текущая модель не описывает, что происходит с уже завершённым Enrollment, если Instructor добавляет новый модуль в курс постфактум (см. ASSUMPTIONS.md, State Machine)
·	Роль-специфичные права доступа (RBAC) как отдельный артефакт — сейчас авторизация отражена частично (через security: bearerAuth и текстовые описания 403), для реального проекта стоит формализовать матрицу доступа отдельным документом
·	Версионирование OpenAPI — при росте API потребуется стратегия версионирования (/v2) и политика deprecation
